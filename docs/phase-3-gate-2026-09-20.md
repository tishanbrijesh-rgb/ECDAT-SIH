# Phase 3 Gate — 2026-09-20

## Outcome

Phase 3's technical gate is green. The database is migrated to the single Alembic head
`0008_scan_admission`; backend, static, frontend-unit, build, and browser gates pass.

## Delivered

### Bounded outputs and evaluation

- Evidence graphs cap assets, nodes, and edges and return explicit truncation metadata.
- Evaluation queries load at most 10,000 assets and reject larger requests with HTTP 413.
- Ground-truth inputs retain the 2 MiB byte cap and now cap assets at 10,000 items.
- Existing CBOM and risk-report interactive endpoints remain paginated; CSV exports stream.

### Authenticated accountability

- Authentication resolves a principal with subject, role, expiry, and session ID.
- Audit events persist and expose principal identity.
- Asset mutation and audit insertion share one transaction and roll back together.
- Retention purge writes an audit event containing actor, parameters, cutoff, and deleted count.
- Revoked sessions are stored in a database deny-list and checked during token validation.
- Migration `0007_audit_principal` backfills existing audit rows.

### Durable scan admission

- Accepted scans and their dispatch outbox entry commit atomically.
- Claims use compare-and-set ownership with expiry and heartbeat renewal.
- Cancellation is persisted so any API replica/worker can observe it.
- Result persistence is guarded by a monotonically increasing result version.
- SQLite foreign keys are explicitly enabled, matching production cascade semantics.
- Migration `0008_scan_admission` adds the dispatch outbox and result version.

## Honest residual gaps

- Full CBOM/text generation is still synchronous; asynchronous immutable artifact generation
  with polling remains future work.
- Evaluation is bounded but still executes in the request worker rather than a separate
  CPU-deadlined worker.
- Session revocation has a persistent backend strategy but no logout/admin revocation endpoint.
- Purge evidence remains in the same retention-managed audit table rather than a separately
  protected administrative stream.
- PostgreSQL multi-process crash/retry behavior is designed through transactional claims but was
  not exercised by this local SQLite gate; it needs a PostgreSQL integration environment before
  a public production release.
